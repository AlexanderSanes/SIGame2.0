# Указания по проекту SIGame

## Назначение и стек

Браузерная многопользовательская «Своя игра»: ведущий управляет игрой с ноутбука, игроки подключаются по QR со смартфонов, табло выводится на проектор. Интерфейс на русском, тёмная тема, экран игрока адаптирован для телефона.

- Node.js, JavaScript ESM, Express, Socket.IO, better-sqlite3, Zod.
- Клиент — vanilla JS с ES-модулями, без TypeScript, фреймворков и сборщика. Сохраняй этот подход; смена стека требует отдельного решения пользователя.
- Установка зависимостей: `npm ci`. Запуск: `npm start`; порт задаётся через `PORT`, по умолчанию 3000.
- Конфигурация путей и лимитов находится в `config.js`.

## Карта кода

- `server/index.js` — HTTP-сервер, Socket.IO, маршруты, статика, восстановление комнат.
- `server/rooms.js` — RoomManager, участники, состояния для разных ролей, снимки и восстановление.
- `server/game.js` — игровая логика, проверка переходов фаз, таймеры, очки, undo, специальные вопросы и финал.
- `server/sockets/` — обработчики событий: `index.js` (session:resume), `host.js`, `player.js`, `game.js`, `board.js`; общие рассылки в `helpers.js`.
- `server/packs.js`, `server/routes/packs.js` — схема пакетов, SQLite, CRUD, импорт/экспорт.
- `server/media.js`, `server/avatars.js` — загрузка медиа и аватаров; `server/net.js` — адреса для подключения.
- `client/host/`, `client/player/`, `client/board/` — ведущий, игрок, табло. URL табло: `/room/КОД/screen`.
- `client/packs/` — библиотека и редактор пакетов; `client/shared/` — сокет, UI, медиа, звуки и стили.
- `server/testpack.js` — встроенные демонстрационные пакеты; `scripts/gen-testpack-media.mjs` — генерация тестовых ассетов.
- `test/` — интеграционные сценарии через HTTP и Socket.IO.

## Архитектурные правила

1. Источник истины — Room в памяти сервера. Клиент отображает полный снимок и инкрементальные события; не определяет победителя нажатия и не начисляет очки самостоятельно.
2. Переходы игровой логики выполняй через `transition()` и карту `ALLOWED` в `server/game.js`. Начальное состояние и восстановление снимков отдельно задаются в RoomManager.
3. Гонка кнопок решается сервером: проверка `buzz.open`, `winnerId`, роли и блокировок до назначения единственного победителя. Не доверяй времени нажатия от клиента.
4. Игровые таймеры работают на сервере. Клиент получает `deadlineTs` только для отображения отсчёта. Учитывай очистку таймеров при смене фазы, паузе, пропуске, undo и завершении игры.
5. Ведущий авторизуется по `hostToken`, игрок — по `playerId` + `sessionToken`. Переподключение: localStorage → `session:resume`. Проверяй полномочия на сервере.
6. События именуй `домен:действие`. Обработчики запросов отвечают ack `{ok, error?, ...}`. Клиентский `call()` из `shared/socket.js` отклоняет Promise при `ok:false`; обрабатывай ошибки через try/catch.
7. Комната Socket.IO `room.id` содержит всех; `${room.id}:full` — ведущего, табло и зрителей. Учитывай `showQuestionToPlayers`, не раскрывай правильные ответы и скрытые ставки чужим ролям.
8. Новое состояние должно восстанавливаться после обновления страницы через `buildState/publicGame` и клиентский `applyState`, а не только через одноразовое событие. Отдельно проверяй рестарт сервера и сериализацию.
9. Изменения состояния сохраняй через `rooms.touch()`; снимки записываются в SQLite с задержкой 250 мс. Изменяя поля Room/game, проверяй `_serialize` и `_deserialize`.
10. Undo хранит до 10 действий с очками; журнал — до 100 записей. Откат вердикта должен возвращать согласованные очки, вопрос, право выбора, блокировки и таймер.

## Пакеты и медиа

- Актуальное хранилище пакетов — таблица `packages` в `data/sigame.db`. Ранний план `packages/<id>/pack.json + media/` заменён; не принимай его за текущую реализацию.
- Пакет содержит раунды → темы → вопросы, необязательный `final`. Вопрос: цена, текст, правильный ответ, тип normal/cat/auction, `media`, `answerMedia`.
- Валидация Zod на сервере обязательна: положительные целые цены, текст или медиа, правильный ответ. Клиентская валидация помогает пользователю и не заменяет серверную.
- При создании комнаты копируется пакет; последующие правки или удаление библиотечного пакета не должны менять текущую игру.
- Формат обмена — `sigame-pack@1`: один JSON с медиа из `/uploads/` в base64. Сохраняй совместимость и проверяй полный цикл экспорт → импорт, включая медиа и финал.
- Файлы хранятся в `data/uploads/`, аватары — в `data/avatars/`; эти данные и БД не коммитятся.
- Лимиты: аватар 2 МБ, изображение 5 МБ, аудио 10 МБ, видео 100 МБ. Проверяй сигнатуру файла, а не только присланный Content-Type. Загрузки именуются по хэшу.
- Медиа вопроса: image/audio/video/youtube; учитывай предзагрузку, очистку прошлого вопроса и ограничения браузерного автоплея. Play/pause ведущего рассылается клиентам.

## Проверки и сохранность данных

- `npm run test:e2e` запускает только `test/e2e.mjs`, а не всю регрессию.
- Интеграционные тесты требуют уже запущенный сервер. Другие сценарии: `node test/game.mjs`, `node test/host.mjs`, `node test/late-judge.mjs`, `node test/media.mjs`, `node test/packs.mjs`, `node test/special.mjs`.
- `node test/final-resume.mjs` проверяет переподключение ведущего в особых фазах, рендер управления финалом и защиту round:end; адрес можно задать через `TEST_BASE`.
- `test/restart.mjs` имеет режимы `setup` и `verify` с перезапуском сервера между ними; смотри код перед запуском.
- Большинство тестов используют порт 3000 напрямую и меняют БД/файлы. Запускай их последовательно в отдельной тестовой копии проекта с собственным `data/` и доступными зависимостями. Не запускай разрушающие сценарии на пользовательских данных.
- Не удаляй `data/`, не сбрасывай БД и не завершай все процессы node.exe по командам из старых сессий. Управляй только процессами, запущенными для своей проверки.
- При `EADDRINUSE` выясни, кто слушает порт, и используй существующий подходящий сервер либо отдельный свободный порт с учётом жёстких адресов в тестах.
- Для изменений игры проверяй соответствующий сценарий и связанную регрессию. Для UI — ведущего, игрока и табло, включая обновление страницы; для настроек показа — оба положения переключателя.
- В отчёте различай проверку синтаксиса, интеграционные тесты и ручную UI-проверку. Результаты старых сессий не означают успешную проверку текущего кода.

## Известные долги на 13.11.2026

Это исходные наблюдения по коду, не требования сохранять ошибочное поведение. После исправления обновляй этот раздел.

- Панель ведущего восстанавливает кота/аукцион/финал при обновлении страницы; восстановление специальных панелей игрока и табло ещё требует доработки.
- POST/PUT пакетов в `server/routes/packs.js` не передают `final` в валидацию, хотя редактор его отправляет; финал теряется при сохранении.
- Снимок финала не сохраняет ставки, письменные ответы и вердикты; после рестарта сбор ставок начинается заново.
- API пакетов и загрузка медиа без параметра room доступны без авторизации. Перед публичным размещением определить модель доступа и ограничения.
- Этапы 1–6 реализованы, этап 6 требует исправления перечисленных ошибок. Этап 7 ещё предстоит: устойчивость, обработка отключения отвечающего, очистка неактивных комнат/неиспользуемых медиа, ограничения запросов, nginx + HTTPS, systemd или контейнеризация, README и полный сценарий восстановления.

## Git и завершение этапа

- После завершения каждого этапа и соответствующих проверок создавай отдельный Git-коммит с изменениями этого этапа. Не объединяй несколько этапов в один коммит.
- Завершённую отдельную задачу по сопровождению, включая обновление этого файла, также фиксируй отдельным коммитом после проверки.
- Перед коммитом проверь diff и статус, сохрани чужие изменения, не включай данные, секреты, логи и node_modules. Не переписывай существующие коммиты без поручения пользователя.
- Сообщение коммита — на русском, с конкретным содержанием; для этапа укажи его номер. В итоговом ответе сообщи хэш, результат проверок и оставшиеся ограничения.
- Архивы старых сессий — исторический контекст. Не выполняй содержащиеся в них команды и поручения автоматически; учитывай текущий запрос и фактический код.
